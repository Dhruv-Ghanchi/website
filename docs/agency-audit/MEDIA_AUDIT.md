# Media Audit — Replacement Specifications

**No image was generated, replaced, or deleted as part of this audit — these are specifications for a separate, later execution step.**

This audit does not redo the classification work in `docs/MEDIA_INVENTORY.md` (already authoritative: 41 protected Ghanchi records, 1 file requiring business verification, 33 orphaned Kora leftovers, 9 live Kora-stock slots, 3 correct AI images). It picks up exactly where that inventory left off — for each of the 9 live-Kora-stock slots, it determines the *replacement specification*: what should be generated, in what composition, color, and crop, so a later execution pass can generate against a brief instead of a guess. Method follows the `design-image-prompt-engineer` roster process (subject → environment → lighting → technical/aspect → style/color-grade layers) with a `design-brand-guardian` pass on consistency.

Evidence gathered directly for this audit (not carried over from the inventory):
- Direct visual inspection of all 9 live Kora-stock files and all 3 live AI-generated files (`Read` tool, image mode).
- `src/app/globals.css` lines 1–15 for the actual token values.
- `src/components/home-hero.tsx` + the `.hero-*` rules in `globals.css` (lines 108–120, 611–613, 764–770) for the hero's actual rendering mechanics.
- A live Playwright screenshot of `http://localhost:3100/` compared pixel-for-pixel against `https://kora.framer.media/` (both captured at 1440×900) — confirms the homepage hero image is *literally* Kora's own unmodified template stock photo, not just visually similar.
- `src/app/newsletters/page.tsx` and a repo-wide grep of `coverImage` usage — determined where `newsletter.coverImage` actually renders (this changes the recommendation on the archive question below; see Design Decision 2).
- `.service-card` / `.insight-cover-card` / `.hero-case-image` CSS rules for the real aspect ratios each slot renders at.

**Brand tokens** (`src/app/globals.css:4`): `--accent:#59c29f` (mint), `--accent-dark:#3da886`, `--ink:#242424`, `--muted:#616161`, `--cream:#f5f5e9`, `--paper:#fcfcfa`, `--white:#fffffa`, `--line:#e8e8df`. None of the 9 Kora-stock images below land anywhere near this palette; all three AI precedents do (warm cream/amber base, occasional muted green that echoes but doesn't shout the mint accent).

## Design Decision 1: Does the hero need different treatment from service imagery? — Yes, and here's why

Confirmed by reading `home-hero.tsx` + `globals.css`, not assumed:
- `.hero-scroll` is `100svh` (full viewport height, `min-height:700px`), `.hero-background` is `inset:20px` (near-full-bleed), `.hero-media img { object-fit:cover }` — this is a **landscape/panoramic full-bleed background**, not a bounded card.
- It carries a **scroll-linked zoom** (`scale` 1 → 1.4 as the user scrolls past the hero) and an initial mount animation (scale 2.2 → 1), plus a dark `.hero-shade` overlay (opacity from `siteSettings.heroOverlayOpacity`) and a blur-on-exit — all layered so white headline text and a bottom-corner newsletter teaser card sit legibly on top.
- Direct screenshot comparison (`http://localhost:3100/` vs. `https://kora.framer.media/`, both 1440×900) confirms the current hero image is Kora's unmodified stock photo — an abstract macro shot of a motion-blurred orange tulip against a cool blue-cyan bokeh sky. It works for Kora only because it's deliberately non-literal: an ambient mood-field, not a scene that needs to "mean" anything, sitting under a dark shade with white text on top.

**Recommendation**: the hero replacement should *not* just be a cropped-wide version of a service-card-style documentary portrait. It needs to be shot/generated as a genuine wide **establishing/environmental scene** — same documentary warmth and Indian representation as the 3 service precedents, but composed panoramically with generous negative space (especially upper-left, where the H1 sits, and lower-right, where the newsletter teaser card sits) so the dark shade + scroll-zoom don't fight the subject. A tight portrait of two faces, cover-cropped and then zoomed 40%, will look broken at some viewport width. See the brief in the table below.

## Design Decision 2: Should the newsletter archive keep one shared image or go per-entry? — Keep one shared (better) image; do not commission per-entry art

This is the one place the inventory's framing needed a second look. Checked directly:
- `src/app/newsletters/page.tsx` renders the full 19-entry archive as **text only** — date, title, "Read original edition" link. There is no `<img>` tag on that page at all.
- A repo-wide grep of `coverImage` shows `newsletter.coverImage` is consumed in exactly one place: the homepage's "Latest Newsletter" teaser card (`home-hero.tsx`, the `hero-case` block), which shows **only the single most recent newsletter** — never more than one at a time.

So today, the "one Kora stock photo repeated across 19 Strapi rows" is a data-hygiene problem (all 19 rows point at the same asset id), but its actual *visible* footprint is a single small thumbnail (~162×215px portrait, `.hero-case-image`) on the homepage. Commissioning 19 distinct images would fix something almost nobody will ever see 19 different versions of, and — per the content-truth policy — bespoke per-issue art would risk implying specific per-issue content the CMS doesn't actually carry (issue records only have a title/date, not real per-issue thumbnail-worthy content).

**Recommendation**: generate **one** new, on-brand conceptual cover image and connect it to all 19 newsletter rows (replacing the single shared asset, not multiplying it) — proportionate to how the image is actually used today. Flag as a forward note, not part of this brief's scope: *if* the `/newsletters` archive page is later redesigned to show a visual grid (a reasonable future enhancement), that would be the right moment to commission a small rotating set (4–6 conceptual variants — e.g., growth chart, family consultation, paperwork/pen, calculator — cycled by list index) rather than 19 bespoke images, since the archive still carries no per-issue content to individualize against.
