# Kora Motion / Animation Audit

Auditor persona: Whimsy Injector (`docs/agency-audit/roster/design-whimsy-injector.md`), applied per that file's actual standard: *audit the brand's own interaction language first; every playful element must serve a functional or emotional purpose; do not propose effects the reference itself doesn't use.*

Method: source-level comparison of `ghanchi-investments/src/components/{home-hero,home-sections,site-shell,ui,faq}.tsx` and `globals.css` against the verified Kora recreation at `C:\Users\Ghanchi\Desktop\trial` (same files), via direct `diff`. Where the two are functionally identical, the values below are taken directly from the shared source — they are Kora's actual template values, not estimates. Numeric parameters (duration, easing curve, stagger, spring constants) are read straight out of the `motion`/Motion-for-React calls, not guessed.

## Summary finding

The motion/interaction system is **almost entirely shared, byte-identical code** between the verified Kora recreation and the current Ghanchi implementation — this was directly verified this session (not assumed from the prior audit) via `diff` across all six shared component files plus `globals.css`. Every scroll-driven scene, spring constant, and hover transform is either unchanged or a superset addition justified by Ghanchi's larger navigation IA. There is no case of Ghanchi *removing* or *breaking* a Kora motion pattern.

## Evidence gaps (NEEDS FURTHER EVIDENCE)

- **Kora's live hover-transform values could not be independently re-confirmed via fresh browser automation this session.** Framer's markup wraps visible button/link text in a nested `<span>`, so `element.hover()` + `getComputedStyle()` against the outer anchor returns the unstyled wrapper, not the actual animated element (background read back as `rgba(0,0,0,0)`, transform as `none` on a visibly-styled pill button) — this is the same DOM quirk already flagged in the base evidence file for `navLink`. The table above relies on the `trial` recreation's source code as the reliable proxy for Kora's real values, which is sound given the CSS/JS diff shows the interaction layer is otherwise untouched — but the exact live pixel-for-pixel hover values on kora.framer.media itself were not re-measured.
- **Mobile-viewport motion (e.g., whether the sticky-statement scene or comparison scroll-scene behave identically at 390px)** was not re-verified interactively in this pass; the existing full-page mobile screenshots are far below a legible scale for motion inspection (a static image also cannot show a scroll-driven animation regardless of resolution). A scripted mobile scroll-and-capture pass would be needed to confirm parity beyond the source-level code match already established.
